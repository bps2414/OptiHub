Do NOT persist Steam detections into `manual_game_registrations` and do NOT create a single shared table that requires Steam rows to satisfy executable-path uniqueness. This is the architectural fix for Phase 3: Steam rows are scanned fresh and reconciled in memory against persisted manual registrations.

Explain the model in code comments near the reconciliation entry point with these exact rules:
- Steam-side authoritative match key in Phase 3 = normalized install root
- manual/manual duplicate prevention = normalized executable path
- executable-path matching between Steam and manual rows is a future enhancement only, because Steam rows do not reliably know their `.exe` yet

Implement reconciliation in `refresh_game_library(app)` and `get_game_library(app)` like this:
1. Load current Steam detections from the Phase 03-01 scan path
2. Load all rows from `manual_game_registrations`
3. Match manual registrations to Steam detections by `normalized_install_root`
4. Emit merged Steam-effective rows with:
   - `id = steam:{appid}`
   - `source = 'steam'`
   - `userAdded = true`
   - `removable = false`
   - `executablePath = manual executable path when a manual registration matched, otherwise null`
5. Emit unmatched Steam rows with:
   - `source = 'steam'`
   - `userAdded = false`
   - `removable = false`
6. Emit unmatched manual rows with:
   - `id = manual:{registration_id}`
   - `source = 'manual'`
   - `userAdded = true`
   - `removable = true`

This lifecycle must explicitly preserve original user-added provenance separately from effective source. If a matched Steam detection disappears on a later refresh, the saved manual registration must reappear as a standalone manual row instead of being deleted or leaving behind a stale Steam row.
